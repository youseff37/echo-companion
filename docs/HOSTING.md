# 服务器自用与多人托管

**单一拥有者把回声部署在自己的服务器上，技术上可行。用户登录一个公共网站后，由平台托管许多人的 QQ，则是另一项尚未实现的产品。** 域名只提供访问入口，不能代替账号隔离、密钥管理、会话恢复和运维。

平台接入方式的具体资料与核实结论见 [云端可行性研究](CLOUD_FEASIBILITY.md)。本文记录本项目当前边界和下一步条件，不构成上线成功声明。

## 三种容易混淆的账号方式

| 方式 | 授权了什么 | 与“扫描个人 QQ，自动聊天”的关系 |
|---|---|---|
| QQ 互联 / OAuth | 用户用 QQ 身份登录一个网站，按授权范围提供相应身份资料。 | 不能因此读取个人 QQ 聊天或接管个人 QQ 消息。 |
| QQ 官方机器人 API | 开发者在开放平台创建机器人，按官方渠道、权限和规则收发消息。 | 机器人身份与用户个人 QQ 账号不同；接入条件和可发送场景应按当时官方文档核对。 |
| NapCat / OneBot | 在用户控制的环境运行 QQ 客户端桥接，再让应用通过协议收发消息。 | 接近本试点的个人机器人 QQ 路径；属于第三方桥接，有重新扫码、掉线和账号风控的可能。 |

[LangBot 的官方 QQ webhook 接入文档](https://github.com/langbot-app/LangBot/wiki/zh-usage-platforms-qq-official_webhook) 体现了官方机器人的 AppID、密钥、服务器和回调配置，与扫码一个个人账号是不同流程。[NapCat #2079](https://github.com/NapNeko/NapCatQQ/issues/2079) 则记录了数据已持久化的多个桥接账号仍需重新扫码的反馈；它是可靠性需求信号，不能用来推断所有云端账号都会失败。

## 路径 A：一位拥有者的服务器实例

一套回声进程、一份私有数据目录和一套专用 QQ 桥接，由同一拥有者管理。这样电脑可以关机，但服务器、网络、模型服务和 QQ 登录状态仍需要维持。

最小拓扑：

```text
拥有者浏览器
    │ SSH 本机端口转发
    ▼
服务器 127.0.0.1:8787 回声控制台
    │ OneBot（同服务器的私有通道）
    ▼
服务器 QQ 桥接 ── QQ 服务
    │
    └─ 回声按用户配置访问 DeepSeek API
```

准备步骤：

1. 选择能运行所需 Docker 镜像架构的 Linux 服务器，安装受支持的 Node.js、Docker，准备独立系统用户和私人目录。
2. 在服务器按 README 安装。应用仍只监听 `127.0.0.1`；不开放回声、NapCat WebUI 或 OneBot 端口到公网。
3. 在自己的电脑建立隧道，例如 `ssh -L 8787:127.0.0.1:8787 -L 6099:127.0.0.1:6099 用户@自己的服务器`。确认本机这两个端口没有被其他实例占用。
4. 从 SSH 会话查看本次启动打印的控制地址，在自己的浏览器打开。按本机流程完成扫码、Key、账号核对和指定会话单次验收。
5. 再决定进程托管、私人备份、更新窗口和停机恢复方式。Node 进程和 QQ 桥接应分别检查；禁止只因为进程活着就认定 QQ 能收发。

这条路径尚需在实际服务器验收，包括扫码、重新登录、重启、备份恢复和网络中断。现有本机测试不能替代它。服务器自用也不需要为了“有网站”先购买域名。

若要提供公网域名入口，应另行设计 HTTPS、持久身份认证、凭证轮换和反向代理边界。当前启动控制 token 不是多用户登录系统。不要把已有应用从 `127.0.0.1` 改成 `0.0.0.0` 后直接上线。

## 路径 B：平台托管多个用户（尚未实现）

目标体验可以是“登录网站 → 绑定专用 QQ → 填自己的模型 Key → 选择回复范围”，但每一步背后都需要新的运行契约：

- **网站身份：** 注册、登录、会话失效、找回与访问审计。网站身份和 QQ 登录状态分开管理。
- **每人独立运行环境：** QQ 客户端、桥接凭证、数据卷、进程与网络边界分开。一个容器名称或一个数据库字段不等于已完成隔离。
- **每人独立权限：** 用户不能查看别人的二维码、联系人、记忆、Key、日志或调用状态；所有 API 和后台任务校验归属。
- **密钥生命周期：** 用户 Key 需要可靠的加密存储与密钥管理、轮换、撤销；不得以普通 JSON 明文作为托管服务默认方案。平台必须清楚告知 Key 和聊天上下文会经过服务器。
- **配额和资源：** 单用户限制、容器资源限制、总并发、排队、超时和失败处理。用户自备 API 不会免除平台的计算、存储与带宽成本。
- **掉线与删除：** 重新扫码提示、过期二维码失效、停止任务、解绑、删除所有副本和备份保留策略。
- **升级与事件处理：** 兼容性验证、逐步升级、回退、可恢复备份，以及平台和用户账号异常的处理渠道。

以上是路线图要求，不是当前实现清单。没有这些能力前，不开放“任意用户输入 Key 后托管 QQ”的公众入口。

## 建议顺序与验收依据

先验证本机单用户，然后用同一产品验证一个自用服务器实例。确认持续运行与恢复成本后，才评估封闭的多人试用。公开托管前，需要额外核对平台准入、服务商与目标部署地区的适用要求。

每条路径都用同一标准判断：**指定对端实际收信、暂停后不再回复、重启不重放、记忆和 Key 不跨用户、异常如实显示。** 模型 API 返回、桥接接口确认或 Docker 进程存活，分别只证明各自那一小段链路。

## 可选 Docker Compose 样例（尚未实机验收）

先在仓库运行 `npm run bridge:init` 生成私有配置，再按服务器架构选择其中一个命令：

```sh
# x86_64 / AMD64
docker compose --profile x64 up -d --build
# 或 ARM64
docker compose --profile arm64 up -d --build
```

不要同时启动两种 profile，也不要同时运行原生 bridge:start 和 Compose。应用容器与对应桥接共享网络命名空间，OneBot 通过内部回环访问；应用在容器内监听全部网卡，宿主端口仍仅映射 127.0.0.1。QQ、记忆分别放在专用数据卷。获取控制链接使用对应 app 服务的容器日志；日志中包含控制凭证，不分享原始日志。此样例不提供网站注册或租户管理，不能拿来当多用户服务。
