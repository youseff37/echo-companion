# 云端 QQ 接入：可行性与产品边界

研究日期：2026-11-01。本文件说明技术选择；不表示已经完成官方机器人权限申请、云端服务或多人托管。

## 先确定用户在和谁聊天

如果用户想“在自己的 QQ 里加一个 AI 好友”，应使用一个**独立机器人账号**，或腾讯官方 QQ Bot。用户自己的日常账号只负责向机器人发消息。

如果用户扫码登录自己的日常账号，程序则可能以这个账号接收好友、群消息并代为回复。这属于**账号自动回复/托管**，不能与“拥有一个 AI 好友”混为一谈。本产品首次引导应明确这一区别，不默认托管用户主号。

## 三条接入路径

| 方式 | 能做到什么 | 不能据此推断什么 |
| --- | --- | --- |
| QQ 互联网站登录 | 用户登录网站，获取获授权的昵称、头像等身份资料 | 不等于授权网站监听私人 QQ 聊天、控制客户端或代发消息 |
| 腾讯官方 QQ Bot | 创建机器人，以 AppID/AppSecret 换取 AccessToken，在机器人获批场景中收发消息 | 不等于扫码托管一个普通 QQ 账号；能力仍取决于平台权限与实际审核状态 |
| NapCat + OneBot | 本机或服务器运行 QQ 客户端，扫码让独立机器人账号上线，通过 OneBot 接入应用 | 不等于腾讯官方机器人接口；不能承诺不会掉线、限流或受到账号风控 |

来源：[QQ 互联 API 列表](https://wiki.connect.qq.com/api%E5%88%97%E8%A1%A8/)、[官方 QQ Bot 启动接入](https://bot.q.qq.com/wiki/develop/api-v2/)、[NapCat 工作方式](https://napneko.github.io/guide/napcat)。

## 官方 Bot 适合怎样的云端体验

可以由服务运营方创建官方机器人，让用户在网站配置自己的模型 Key，再在 QQ 中与该机器人对话。服务端将 QQ 用户标识与其配置、记忆、额度关联；群聊需要单独明确配置归属和谁为调用付费。这样不必为每位用户托管一个完整的个人 QQ 客户端。

现行官方线上文档列有 C2C 单聊、群 @、全量群消息事件、单聊流式消息及发送频控。是否可用仍须在实际账号和目标群验证，不能仅根据文档列出接口就宣称拥有权限。API 凭证应只在服务端使用，并处理过期与刷新。[消息概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)、[访问凭证](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/access-token.html)。

注意时效：旧 `tencent-connect/bot-docs` 仓库中的部分消息规则与现行线上 wiki 不一致。实现时优先核对线上具体接口和实际响应，不沿用旧文章里的能力限制或额度。

## 个人服务器自托管可以先做

NapCat 的官方项目文档已提供 Linux Docker 部署、数据卷和 WebUI 登录流程。将一个机器人账号、一个应用实例部署在自己的服务器上，技术上可行。电脑不必持续开机，但服务器要持续运行并能访问 QQ 和模型服务。

部署时应分别呈现三个状态：**容器运行、QQ 登录、OneBot 连接**。其中任何一个正常都不代表另外两个正常，也不代表实际消息已送达。[Docker 部署](https://napneko.github.io/guide/boot/Shell)、[连接应用端](https://napneko.github.io/NapCatQQ-Desktop/docs/connections/)。

NapCat 管理页与 OneBot 使用不同的端口和凭据；默认只绑定回环或内部网络。远程管理使用可信隧道或具备独立鉴权和 TLS 的入口，不直接公开未经保护的管理接口。首次真实聊天应限定会话、只验收一次，并由接收者确认。[NapCat 安全说明](https://napneko.github.io/other/security)。

## 多人托管不是给单机版加一个注册页

公开服务至少还需要以下工程能力；当前实现不宣称已具备这些能力：

- 每个机器人账号独立实例、账号数据卷与连接令牌；配置、记忆、任务队列和用量均按租户隔离。
- 网站用户只能访问自己的实例；管理与调度服务不接受任意镜像、宿主机挂载或 Docker 参数，也不向用户暴露 Docker socket。
- 处理二维码过期、手机确认、重新登录、凭据轮换、风控和断线；自动重试要退避，发送结果不明时不得重复发送。
- 模型 Key 需服务端密钥管理、访问控制和日志脱敏；聊天、备份和账号登录态需明确保留、导出和撤销流程。
- 每实例 CPU、内存、磁盘、并发和模型调用上限；一个账号的异常不能耗尽整台机器。
- 自定义模型地址、插件与工具调用需单独设计云端边界，防止任意访问服务器内部地址或执行宿主机代码。

Docker 的 namespaces 和 cgroups 提供基础隔离与资源约束，但不替代应用层租户授权。Docker 官方特别提醒，网站通过 API 创建容器时必须严格限制参数与 daemon 控制权限。[Docker Engine 安全](https://docs.docker.com/engine/security/)。

用户自带 API Key 只转移模型账单，不会消除实例运行、磁盘、网络和维护成本；也不意味着托管方无法接触 Key 或发给模型的聊天内容。资源容量应以真实账号压力测试估算，不能承诺一台服务器无限托管。

## 推荐交付顺序

1. **本地开源版：**独立机器人账号、用户自带 Key、本机可控的会话与记忆；提供 AI 可读的安装和验证说明。
2. **单用户服务器版：**复用同一核心，验证持久化、重启、扫码、实际收信、暂停与备份恢复。
3. **云端方向验证：**优先评估官方 Bot 的获批能力及用户体验；如果坚持个人 QQ 托管，先做受限名额的封闭测试，获得账号稳定性与单实例成本数据。
4. **公开多人服务：**完成租户隔离、密钥管理、配额和运维验证之后再承诺提供。

以上路线是基于已核对资料的工程建议。当前不保证平台权限、账号长期在线、第三方桥接的稳定性或国内任意网络的可达性。
